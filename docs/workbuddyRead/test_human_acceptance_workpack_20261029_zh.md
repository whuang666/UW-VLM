## 2. 每条只围绕4个问题裁决

1. **可辨认**：每个保留帧中的目标，以及scope用到的其它对象是否可辨？不能仅凭任务名或前后帧猜本帧有物体。
2. **谓词可判**：对每帧独立填写所有保留谓词。OnSeabed要有实际支撑证据，InGripper要有夹持与相邻画面共同运动证据；夹爪信号或DVL只作辅助。NextTo采用抓取前approach语义，NearBox采用释放位置附近语义。
3. **转移可判**：各相邻帧对是否具有ego可以判定、且非空的变化？transfer的grasp→at_box跨段单独看，不从末帧推定隐藏的lift；缺失中间运动证据须记录。
4. **选帧符合规则**：稳定状态、源帧绑定、现行事件窗口、至少20帧的数值下限以及至少2个真实渲染更新是否满足？页面的灰度阈值段只供定位，不能代替真实更新次数或物理事件时间。

所有scope谓词都要填true／false／未定；“未定”不能编译成false。如果仅某个谓词无法在全部保留帧判断，应从整条episode的scope移除后另建版本，不能只删该帧的值。Lifted不在本批scope；transfer也没有OnSeabed，不能通过at_box偷偷带回“已离底”。

## 4. 导出后如何检查

导出文件名默认为`completed_reviews.json`。填写页可保存部分进度，但空表或部分记录不能通过完成性检查。

在仓库根目录运行校验，输出使用新的文件名：

```powershell
$py = 'C:\Users\whuang\.workbuddy\binaries\python\envs\default\Scripts\python.exe'
& $py -X utf8 ENACT/scripts/usim/validate_acceptance_reviews.py `
  --reviews 'C:\path\to\completed_reviews.json' `
  --out ENACT/docs/WBW/evidence/test_human_acceptance_20261029_v1/review_validation_completed.json
```

脚本不修改复核表或数据。exit2表示记录不完整／不合规；exit0只表示10条处置记录齐备。**“完成复核处置”与“当前10条都accepted”分开报告**：9条接受、1条排除时，也需要先重建9条新版本；exit0不等于可以跑正式test。

校验器检查工作包／候选快照／annotation／PNG哈希、episode与帧绑定、真实复核者自声明、逐帧scope、转移、4项问题、签名、带时区日期及分歧。即使程序检查全部通过，它仍固定`release_eligible=false`，最终发布条件需按下一节完成。

对于1650@f0，当前已知阻塞保留；若另一人有明确相反证据，先形成独立裁决材料并修订该阻塞的版本，不能靠在表里勾“是”自动放行。

## 5. 签字后如何进入最终冻结

按依赖执行，保留全部原始表和否决理由：

1. 将完整复核JSON、校验报告、签字身份／独立性声明和争议裁决作为不可覆盖的版本化证据保存。导出、验证或文件哈希不会自动认证人的身份；身份由项目负责人核实。
2. 从裁决结果产生新候选清单；对接受项保留实际帧和scope，对改帧／移出scope／降级／排除项记录父版本、原因及前后hash。未定项不进入最终test，也不按模型成绩挑保留项。
3. **重新构建QA与图片**并重新分配均衡排列。重新枚举唯一性、oracle、源帧对齐、可见性元数据／视觉判定一致性、常量／文本基线、图文绑定与资产重建，不能继承旧20题通过回执。
4. 冻结manifest同时绑定：最终episode／帧／scope／split、annotation和原视频来源哈希、QA／prompt／图片／字体／映射策略版本、完整复核及裁决回执、源码、模型请求与预算、计分和按episode分组统计方案。人眼裁决与机械门禁必须指向同一组最终输入哈希。
5. 最后验证完整冻结及图片重建路径，再执行一次正式test。inverse单列报告，并同时给出随机期望和确定性文本基线；当前inverse程序基线10/10，不能作为视觉能力证据。

目前除人眼外还有确定的工作依赖：1650处置导致的新版本重建、条件派生A/B/C/D、最终请求协议／统计权重与执行冻结。并非签字之后直接运行旧20题即可。

## 6. 图片入库策略：采用排除新PNG，保存文字与重建证据

已在[ENACT/.gitignore](../../ENACT/.gitignore)追加：

```gitignore
/data/usim_enact/usim-enact-v*/**/*.png
```

这条规则只影响尚未跟踪的PNG，不会删除或取消历史跟踪，也没有改写冻结输入。annotation、QA、manifest、snapshot等文本仍可显式入库；临时复核图继续使用原有_review忽略规则。

实际跟踪范围纠正如下：

| 版本 | 已跟踪文本／总文件 | 已跟踪PNG | 当前本地PNG |
|---|---:|---:|---:|
| v0.1 | 总557 | **504** | 504 |
| v0.2 | **89** | 0 | 1672 |
| 新均衡候选v1 | 0 | 0 | **128**（32raw＋32segmented＋64标号图） |

因此“v0.2整个版本未跟踪”不准确；它已有89份文本入库。新候选7,200,915字节的PNG体积覆盖128图，64只是模型展示图数量。

`git add --dry-run`只针对新数据目录检查：可加入33份文字／JSON文件，PNG为0；没有真的stage或commit。忽略规则不替代显式选文件，也不要force-add数据PNG。新候选的JSON和源标注应在验收及版本定稿后显式归档，原USIM录制继续外置。

图片本地策略下，发布检查还应验证**从保留的标注＋固定源数据＋重建脚本能恢复所有图片及哈希**。当前构建器还从本地`_expansion/`读取保守候选，不能仅凭代码在repo就声称全新克隆已可完整重建；新版本定稿时需一并保存这些紧凑输入或提供有哈希的可下载标注包。
